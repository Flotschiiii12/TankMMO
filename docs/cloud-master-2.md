## Tasks, in this order

### 1. CI and an end-to-end smoke test
The repo has no CI. Add `.github/workflows/ci.yml` (Node 24, `npm install --legacy-peer-deps --ignore-scripts`, lint, test, build; cache npm). Add a Playwright end-to-end smoke test as a separate opt-in job/script (`npm run e2e`): start `npm run server` on a random port with a temp DB and `LOAD_TEST=1`, build the client, open the app in headless Chromium, pass the age gate, create a guest account, join, move with the keyboard, auto-fire, open the inventory, assert the HUD shows, no page errors, and the player position changed. Make it deterministic and under 90 s. Document in `docs/TESTING.md`. If Playwright browsers cannot be installed in this environment, still write the test and CI job and say it is unverified.

### 2. Fuzzing and property tests for the protocol, actions and economy
Write a fuzz harness (`test/fuzz.test.ts` plus `scripts/fuzz.ts` for longer runs) that connects real WebSocket clients and sends random and mutated messages (every `ClientMessage` type with random/NaN/Infinity/negative/huge/wrong-typed fields, truncated and oversized frames, binary frames, prototype-pollution keys, unicode edge cases, message floods). Invariants to assert after every run: the server stays up, no uncaught exception, wallets never negative or non-finite, inventory counts consistent, no item duplication across trade/auction, the DB reload gives the same character. Also add property tests (random sequences of valid actions: craft/upgrade/dismantle/fuse/sell/buy/trade/auction) for conservation of value. Fix every bug you find and list them in the report.

### 3. Close the design-level security items
From `docs/SECURITY_REVIEW.md` "design-level, not changed": (a) abilities and ammo types must be gated by the equipped loadout/unlocks server-side; (b) trades need a distance/safe-zone rule; (c) per-IP throttling of failed joins and of account creation with exponential back-off, without locking out players behind a shared NAT (use the TRUST_PROXY aware IP); (d) the tick loop must isolate failures per instance (try/catch around each instance step and snapshot, log with `log('error', ...)`, quarantine an instance that throws repeatedly by moving its players to a fresh instance instead of crashing the process); (e) server-side plausibility checks for shots (projectile origin near the shooter, rate vs reload time, range vs weapon range) and for movement speed (teleport detection with a tolerance and a graceful correction, not a kick). Each with tests, including a test that proves the old behaviour was exploitable.

### 4. Combat balance simulator and tuning
Build `scripts/balance-sim.ts`: headless duels and group fights using the real sim (`shared/sim`) for all 5 classes x 10 tiers x main weapon families, against each enemy archetype, elites, mini/world/dungeon bosses and in PvP mirror/cross-class matchups. Output tables of time-to-kill and win rates to `docs/BALANCE_REPORT.md`. Targets from `docs/GDD.md`: normal enemy 5-15 s, elite 30-60 s, boss 3-8 min for a group, PvP 20-40 s. Tune data tables (`shared/data`, stat scaling in `shared/rules/power.ts` etc.) so that outliers move into the target bands without breaking existing tests; no class/weapon may dominate (document the spread, for example best/worst win-rate ratio). Add guard tests that fail if a TTK leaves its band by more than a tolerance.

### 5. Progression and economy tuning to the design targets
Targets: level 30 in about 20 h, level 60 in about 120 h, level 100 in about 500 h at a realistic kills/hour; sinks roughly 60-100 % of faucets per level band; top gear very grindy but possible without paying. Extend `scripts/econ-sim.ts` with realistic player behaviour (travel, deaths and repair costs, ammo use, crafting, upgrade failures, market) and print per-band time-to-level and faucet/sink tables. Tune `shared/rules/progression.ts` (XP curve, `KILL_XP_RATE`), loot tables, upgrade costs and repair costs. Write `docs/ECONOMY_REPORT.md` with before/after numbers and add guard tests for the time-to-level bands. Keep premium currency disabled behind the flag, but add a simulation of how many weeks of play a free player needs for the best gear vs a hypothetical paying player to prove the "very grindy but fair" rule.

### 6. Versioned database migrations and backup/restore verification
Replace ad-hoc `ALTER TABLE` checks with a small versioned migration framework (`schema_version` table, ordered migrations, each in a transaction, idempotent, downgrade refused with a clear error). Create fixture databases for every historical schema state you can reconstruct from git history and test that all migrate cleanly to the latest with data intact. Add `scripts/verify-backup.ts`: restores the newest backup into a temp DB, runs `PRAGMA integrity_check`, row-count sanity checks and a profile-load of every account; document in `docs/DEPLOY.md`. Add a test for the automatic daily backup (retention of 14, consistent snapshot while writes happen).

### 7. Clan item storage and alliances
Known gaps from `docs/PROGRESS.md`: clan storage holds scrap only, no alliances. Implement: (a) a shared clan item storage with capacity that grows with clan research/level, deposit and withdraw permissions by role, per-member daily withdraw limits, an audit log, and protection against duplication (atomic DB operations, tests with concurrent requests); (b) clan alliances (propose, accept, break, max 2 allies, cooldown on re-allying, allies cannot be attacked in faction-war control points and share a chat channel); (c) UI in the clan tab (storage grid using the existing item rendering and icons, alliance panel); (d) protocol additions backwards compatible; (e) thorough server integration tests.

### 8. Arena spectator mode
Implement read-only spectating of arena matches from the hub: list of running matches (mode, league, teams, round score), join/leave as spectator (capped number of spectators per match, not counted against instance capacity, cannot send commands), receives a reduced snapshot stream that never leaks hidden fields (no ammo/cooldown details of players) and is delayed by a few seconds to prevent stream-sniping help, camera follows a chosen player or free-roam in the arena bounds, HUD shows round score and timer (reuse the existing arena HUD chip). Server side in `server/gameServer.ts` (keep it modular, extract to a new file if it grows), client UI, tests including "spectator cannot affect the match" and "spectator receives no private data".

### 9. German names for all data-driven content

### 10. Server scaling spike, measurement first
Profile says snapshot building and sending is about 50 % of server CPU under load. Using `npm run bots` (add scenarios: 200 and 400 bots, clustered at spawn and spread across 3 maps, 60 s each, with warm-up excluded) record avg/p95/max tick and bytes/s into `docs/SCALING_REPORT.md`. Then try the most promising change with the best expected gain per risk, in this order of preference: (1) cheaper per-client work (spatial grid for visibility instead of scanning all entities per client, reuse of typed buffers, skipping empty deltas, adaptive snapshot rate under load); (2) moving per-session encode + socket write into worker threads; (3) one process per map group. Keep every existing test green. Keep a change only if the measured gain is clear (at least 25 % lower tick at 400 clustered bots) and correctness tests pass; otherwise revert it and write down the numbers and why. This task is allowed to end with "no change, here is the data".
